# Архитектурный разбор: почему startapus-browser ходит по кругу

Документ фиксирует диагноз и целевую архитектуру. Он заменяет серию точечных правок
в `panel.tsx` — каждая из них лечила симптом и порождала следующий.

## 1. Что происходило (симптомы в хронологии)

| # | Симптом | Что я правил | Что породило |
|---|---|---|---|
| 1 | Пустая панель | убрал `preload`, потом ловил attach | — |
| 2 | Вторая вкладка не открывалась | `multiple: true` | вкладок стало больше, а канал остался один |
| 3 | Команды уходили не в ту вкладку | `tab` в команде, `targetKey`, фокус | цель закреплялась на неактивной вкладке |
| 4 | Вкладки «пропадали» из реестра | порог живости 15 → 120 с | порог не лечит причину тишины |
| 5 | Пустые страницы во всех вкладках | убрал close-handler | причина осталась |
| 6 | Закрытие одной вкладки убирает панель | пытался освобождать lease в close-handler | двойное освобождение → зависший `acquire` |

Каждая правка была локально верной и глобально неверной, потому что все они бьют в одно
место: **жизненный цикл браузера привязан к React-компоненту вкладки**.

## 2. Корневая причина (одна)

Сейчас `PanelBody` (963 строки) владеет **всем сразу**:

- `<webview>` гостя (создаёт, вставляет, удаляет);
- lease (acquire/release);
- long-poll канал к агенту (свой цикл на каждую вкладку);
- очередь команд и их исполнение;
- состояние страницы (URL, scroll, title);
- UI (адресная строка, тулбар, пикер, статус).

Из этого следуют все симптомы:

1. **Вкладка = процесс.** Пока компонент смонтирован, живёт канал. DSH не обязан держать
   неактивные вкладки смонтированными (и приглушает таймеры, если держит) → канал умирает
   или заикается → команды агента стучатся в мёртвую очередь (`queued: 1`), а `targetKey`
   выбирает именно её.
2. **Закрытие вкладки = освобождение lease из UI-кода.** Кто владеет teardown — ядро или
   плагин — не определено. Я пробовал оба варианта: «освобождаю сам» → утёкший/двойной
   release → зависший `acquire` → пустые страницы у всех; «не освобождаю» → утечка.
3. **Несколько вкладок = несколько конкурирующих каналов.** Появляется второй писатель
   состояния (`tabState`, `targetTab`, `knownTabs`, `liveness`, `repin`). Это уже
   распределённая система без консенсуса, поэтому каждое новое правило рождает гонку.

Вывод: **проблема не в конкретном флаге, а в том, что у нас нет единственного владельца
браузерного движка и канала.** Пока владелец — компонент, любое изменение поведения
вкладок (мульти-таб, закрытие, переключение, приглушение) будет ломать приёмку.

## 3. Инварианты, которые обязаны выполняться

1. **I1. Гость живёт вне React.** Создание/уничтожение `webview` и lease не зависят от
   mount/unmount компонента вкладки. Компонент — только вид.
2. **I2. Канал один.** Один long-poll цикл на плагин, один писатель состояния. Никаких
   `tabState`/`targetKey`/liveness-эвристик в маршрутизации.
3. **I3. Вкладка — это запись сессии, а не компонент.** `{ tabId, url, scrollY, title }`
   в таблице движка; переключение вкладки = `activate(tabId)`, а не новый гость.
4. **I4. Ядро владеет закрытием.** Плагин не освобождает lease для вкладки, которую
   закрывает ядро; он лишь забывает сессию (позже — по факту `destroyed`).
5. **I5. Наблюдаемость по одному каналу.** `stage`, `status`, `hasGuest`, `url`,
   `counters` пишет движок; host только читает.

## 4. Целевая архитектура

```
┌────────────────────────────── renderer ──────────────────────────────┐
│                                                                      │
│  engine.ts  (singleton, создан в apply())                            │
│   ├─ sessions: Map<tabId, Session>                                   │
│   │    Session = { container, webview, lease, url, scrollY, title }   │
│   │    контейнеры лежат в document.body (position: fixed), активный   │
│   │    виден и позиционируется по rect панели, неактивные скрыты      │
│   ├─ lease: acquire/release только здесь (по одному на сессию)       │
│   ├─ sessions: Map<tabId, {url, scrollY, title, lastActiveAt}>       │
│   ├─ transport: один poll-цикл (2.5 с) + report                     │
│   ├─ commands: исполнение (open/select/act/verify/capture/...)       │
│   └─ setRect(rect): контейнер позиционируется по прямоугольнику      │
│      панели (ResizeObserver + scroll панели)                         │
│                                                                      │
│  panel.tsx  (тонкий вид, ~150 строк)                                 │
│   ├─ mount(tabId)  → engine.activate(tabId)                          │
│   ├─ rect          → engine.setRect(...)                             │
│   ├─ unmount       → engine.detach(tabId)  (guest НЕ освобождает)    │
│   └─ UI: адресная строка, тулбар, статус (читает engine.state)       │
└──────────────────────────────────────────────────────────────────────┘
```

Почему fixed-контейнер, а не `<webview>` внутри панели: перемещение `<webview>` в DOM
уничтожает гостя (проверено), поэтому контейнер создаётся в `document.body` и
**позиционируется** по прямоугольнику панели. Панель отдаёт `getBoundingClientRect()`
при mount/resize/scroll; контейнер имеет `position: fixed; z-index` и обрезается.

Гость — **один на вкладку** (как в браузере): сессии создаются лениво при первом
открытии, живут до закрытия вкладки, поэтому переключение вкладок ничего не
перезагружает. Канал к агенту при этом остаётся **один** — его держит движок.

Следствие: количество вкладок больше не влияет на канал; неактивные вкладки не
приглушают ничего, потому что опрашивает движок, а не компонент.

## 5. План миграции (без больших взрывов)

| Шаг | Что делаю | Проверка |
|---|---|---|
| S1 | `client/engine.ts`: lease + гость + контейнер + rect; UI не трогаю | `npm run build`, `check-apply`, панель работает как раньше |
| S2 | Переношу transport и исполнение команд из панели в engine; панель только делегирует | `selftest` 45/45, живой `ui_status/ui_open` |
| S3 | Сессии: `openTab/activate/closeTab/list` внутри engine; убираю `tabState`/`targetKey`/liveness из host | команда идёт во **вкладку-сессию**, не в компонент |
| S4 | Панель сокращаю до вида; вкладка закрывается ядром, сессия забывается | сценарий «4 вкладки → закрыть одну» вживую |
| S5 | Удаляю мёртвый код (`tabState`, `pruneTabs`, `TAB_*`, `closeTabResult`-костыли) | `tsc`-чистота, отсутствие дублей |

## 6. Критерии приёмки рефакторинга

- **A1.** Открыть 4 вкладки: `/health.tabs = 4`; переключение любого количества раз не
  меняет число живых гостей (гость один).
- **A2.** Закрыть одну вкладку из четырёх: панель и остальные вкладки живы, `acquire`
  не зависает, `queued` не растёт.
- **A3.** Команда `ui_select/ui_act/ui_verify` исполняется в **активной** вкладке без
  репинов и порогов живости (нет понятий `targetKey`/`liveness`).
- **A4.** `ui_screenshot` создаёт файл (сейчас чинится отдельно: `toDataURL`).
- **A5.** `npm run selftest` 45/45, `check-apply` PASS, живой `/selftest` не меняет
  маршрутизацию (после S3 понятия маршрутизации не остаётся).

## 7. Что не делать (анти-паттерны этой сессии)

- Не добавлять пороги живости, репины и «автопереходы цели» — это лечит последствие.
- Не освобождать lease из UI-кода вкладки.
- Не хранить состояние страницы в React-состоянии компонента.
- Не чинить мульти-таб, пока канал привязан к компоненту: сначала I1/I2.

## 8. Оценка

S1–S2 — механическая работа, риск низкий (guest/lease/transport переезжают без смены
поведения). S3 — главный шаг, убирает целый класс багов. S4–S5 — сокращение кода.
Ожидаемый эффект: `panel.tsx` ~963 → ~150 строк, `index.ts` теряет `tabState`,
`targetKey`, `pruneTabs`, `TAB_*`, `knownTabs` (~150 строк), исчезают гонки маршрутизации.
