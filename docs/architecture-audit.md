# Аудит архитектуры браузера и эталон ядра

Дата: 2026-11-16. Предмет: `startapus-browser` (наш плагин) против встроенного браузера DSH
(`@deepseek-ai/dsh-client-ui-sidebar-browser`), который в приложении работает стабильно.

Симптомы, которые разбирались: мигание страницы, чёрный экран, «открываю…» навсегда,
двойные/лишние загрузки, потеря адреса и сессии при переключении, разные панели с разными версиями.

## 1. Как сделан эталон (встроенный браузер DSH)

Файл: `node_modules/@deepseek-ai/dsh-client-ui-sidebar-browser/lib/client.js` (внутри app.asar).

Ключевые решения:

| # | Решение | Где |
|---|---|---|
| R1 | **Guest живёт ровно столько, сколько смонтирована панель.** `mount()` → `initialize()` → `createGuest()`; `unmount` → `dropGuest()` + `release(lease)` | `ElectronWebviewPresentation.mount/unmount`, `dropGuest` |
| R2 | **Один guest на панель, создаётся один раз**; повторная инициализация запрещена (`if (this.element !== void 0) return`) | `initialize()` |
| R3 | **Никакого измерения видимости и `display:none`**: элемент просто вставляется в контейнер (`host.append(element)`) | `present(element)` |
| R4 | **Никакого глобального reconcile-цикла**: события webview (`dom-ready`, `did-navigate`, `did-fail-load`, `render-process-gone`) двигают состояние | `createGuest()` |
| R5 | **Явная машина состояний UI**: `loading`, `target`, `address: 'requested' | 'observed'`, `error`, `canGoBack/Forward`, заглушки «Opening…», «Restore page», «Load failed» | `store.set(...)`, locales |
| R6 | **Checkpoint адреса** сохраняется (`persist(target)`) и на следующем монтировании восстанавливается | `persist`, `browserAddressCheckpoint` |
| R7 | **Lease = одноразовый ресурс**: освобождается в `dropGuest/release`, ошибки release логируются, но не рушат UI | `release()` |
| R8 | **Ошибки загрузки — событие, а не молчание**: `did-fail-load` (кроме `-3`) → `failed({code, description})` | `createGuest()` |
| R9 | **Workspace-ключ для партиции**: `cwd:<путь>` либо `session:<id>` — стабилен между вкладками одной сессии | `browserWorkspace()` |
| R10 | **Ревизии команд**: `revision++` на каждую навигацию, поздние ошибки старых ревизий игнорируются | `navigate/loadPending` |

Следствие: переключение вкладки не «моргает» — панель либо показывает живой guest, либо
заглушку восстановления; нет цикла hide/show, нет пересоздания без причины.

## 2. Как сделан наш браузер

Файлы: `src/client/engine.ts` (движок, ~2000 строк), `src/client/panel.tsx` (React-панель),
`src/client/transport.ts` (канал), `src/index.ts` (host, инструменты).

Ключевые отличия:

| # | Наше решение | Проблема |
|---|---|---|
| O1 | `sessions: Map<tabId, Session>` + `paneState: Map<tabId, {url, host, visible}>` + **reconcile каждые 500–700 мс** | Устойчивое состояние зависит от таймера и эвристик, а не от фактов |
| O2 | `position(session, visible)` пишет `display: flex/none` | Скрытие живой панели → ядро отцепляет guest → чёрный экран/перезагрузка |
| O3 | Видимость вычислялась по геометрии предков (`getBoundingClientRect` по 10 уровням) | Ложные «скрыто» из-за нулевых обёрток → мигание (исправлялось 0.26.1…0.26.5) |
| O4 | При перемонтировании панели `initialUrl` заново писался в `paneState.url` | Адрес сбрасывался на стартовую страницу (0.26.0) |
| O5 | Много клиентских инстансов (по панели на вкладку), у каждого свои `sessions/paneState` | Статус/URL/очередь команд «прыгают» между инстансами; `revMatch: false` |
| O6 | `reviveBlankGuest` + recovery-циклы | Лечили симптом; при отсутствии лимита — цикл перезагрузок (E25) |
| O7 | Host-очередь команд без привязки к guest, атрибуция по последнему активному инстансу | Команды иногда попадают не в ту панель |
| O8 | Нет checkpoint-хранилища адреса между монтированиями, кроме `sessionStorage` | После полного перезапуска панель стартует с дефолта |
| O9 | Ошибки загрузки показывались только статусом (баннер добавлен в 0.26.3) | Пользователь видел «мёртвую» страницу |
| O10 | Партиция ядра не persist (`dsh-sidebar-browser-<uuid>` без `persist:`) | Сессии сайтов сбрасываются при перезапуске DSH (не наша вина, см. kernel-request) |

## 3. Сопоставление симптомов и причин

| Симптом | Ближайшая причина | Код |
|---|---|---|
| Мигание страницы | O2+O3: наш hide/show по геометрии | `panel.tsx` visibility poll, `engine.position()` |
| Чёрный экран | O2: скрыли видимую панель, guest отцепился до nav; O6: пустой about:blank | `position()`, `reviveBlankGuest()` |
| «открываю…» навсегда | guest отцеплён/скрыт, `loadURL` не доехал | `openInSession`, `loadPending` |
| Адрес прыгает на startapus.com | O4: initialUrl перетирал paneState | `panel.tsx` setPaneState |
| Команды в чужую панель | O5+O7 | `src/index.ts` ownership gate, `transport.ts` |
| Сессия сайта сброшена | O10 (ядро) | `lib/main.js` DesktopBrowserGuests |
| Панели с разными версиями | клиент грузится с диска при монтаже; старые панели живут | `panel mount` |

## 4. Системные корни (не симптомы)

1. **Жизненный цикл guest привязан к эвристикам видимости, а не к монтированию панели.** Ядро
   владеет раскладкой и attach; плагин не должен решать «видимо/невидимо» по геометрии.
2. **Состояние размазано по инстансам и таймерам.** Нет единого владельца состояния на окно;
   reconcile — вторая, конкурирующая машина состояний.
3. **Нет детерминированной машины состояний UI.** Нет явных `loading / ready / failed / restore`;
   поэтому любой сбой выглядит как чёрный экран или мигание.
4. **Нет контракта «одна панель = один guest = один lease».** Пересоздание/переиспользование
   решается на ходу, из-за чего recovery-циклы и лишние загрузки.
5. **Диагностика появилась позже кода.** Без обязательных событий жизненного цикла причина
   каждого мигания выяснялась задним числом.
