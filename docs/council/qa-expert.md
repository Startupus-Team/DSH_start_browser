## 6. Процесс: как сделать `live` гейтом и зафиксировать контракт

### 6.1. Гейт из трёх шагов (один вход, разные коды выхода)

```
npm run gate   = build → selftest (офлайн) → live (E2E, нужен запущенный DSH)
exit 0 = FRESH + E2E зелёный
exit 1 = регрессия кода (selftest/E2E)
exit 2 = STALE (процесс не на этой сборке) — «перезапусти приложение»
exit 3 = нет транспорта (вкладка не открыта) — не путать с регрессией
```

Обязательные условия, без которых `live` гейтом быть не может:

1. `STALE` и `transport:false` **валят** команду (сейчас не валят — P0-2).
2. `live` **не меняет** живое состояние: `/selftest` не должен чистить очередь и жечь лимиты агента (сейчас меняет — P1-4). Пока это не исправлено, гейт допустим только «на холодном процессе».
3. В `live` есть E2E-блок: отрисовка (`textLength>0`), снимок (≥ порога), round-trip команды с корреляцией, `verify` с `pass` на известной странице.
4. Повторяемость: 20 прогонов подряд, флейки ≤ 1; иначе гейт станет «красным по утрам» и его выключат.

### 6.2. Контракт версии ядра (H11 — риск обновлений)

- `package.json.version` — единственный источник; `CHANGELOG` верхняя секция обязана совпадать; `buildRev` попадает в `/health` (уже есть: `index.ts:141-172`, `871`; `scripts/build-rev.mjs`).
- `/health` должен отдавать не только флаг `capabilities`, но и **требуемые API ядра**, которыми пользуется плагин: `sidebarRight.openTab`, `registerCloseHandler`, `keepMounted`, `dshDesktop.browser.acquire/release`, слоты `sidebar.right.pane.tab[.title]`. Форма: `kernel: { version, features: { openTab: true, closeHandler: false, keepMounted: true } }`.
- При активации: отсутствующий feature не валит boot (как сейчас), но попадает в `/health.kernel.missing[]` и в строку статуса — чтобы деградация была видна, а не выглядела как «ничего не происходит».
- Тест: подменить контекст без `registerCloseHandler` → `/health.kernel.missing` содержит его, `apply` не бросает.

### 6.3. CHANGELOG и матрица ТЗ

- Каждая строка «Исправлено» обязана иметь `(test: <id>)`: id — имя проверки в одной из сюит. Без id запись не принимается. Это то, что превращает CHANGELOG из дневника в регрессионный индекс.
- Матрица `startapus-browser-compliance.md` **генерируется** прогоном (`npm run matrix` → прогон сюит → markdown), а не пишется руками: сейчас в одном файле `19/19`, `27`, `24/24`, `42/42` (строки `4,116,148,149`). Живые доказательства в матрице — ссылкой на `~/.dsh/startapus-host.log` с timestamp и rev, иначе они не проверяемы.
- `docs/live-acceptance.md` — исполняемый чек-лист: каждый пункт = команда + ожидаемый exit-код (сейчас часть пунктов устарела: `35+9` проверок и `19/19` при фактических 61/42).

### 6.4. Критерии «готово» для плагина (Definition of Done)

1. `npm run build` входит в `selftest`; rev-guard зелёный (P0-1).
2. Все P0/P1 строки таблицы §3 имеют автотест; каждый проверен «откатом фикса → красный».
3. `npm run selftest` — офлайн, без приложения, < 60 с, детерминированный (никаких сетевых/таймерных зависимостей).
4. `npm run live` — FRESH + E2E, коды 0/1/2/3; `/selftest` не меняет живое состояние.
5. Контракт ядра виден в `/health.kernel`; деградация без падения boot.
6. `package.json.version === CHANGELOG[0].version`, rev в `/health` совпадает с `buildRev()`; матрица сгенерирована.
7. Регрессия из предыстории («гость не рисовался», «бесконечная перезагрузка», «молчащий провал», «падение boot») имеет по тесту, и тесты запускаются до живой приёмки, а не после.
