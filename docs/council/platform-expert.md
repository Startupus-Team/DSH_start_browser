## 1. Находки

**P0 | Панель пустая при возврате на ранее активную вкладку: видимостью управляет движок, а не ячейка вкладки**
`activateSession` прячет inline-`display:none` контейнеры ВСЕХ остальных сессий (`engine.ts:331-334` + `169-171`), а `activeTabId` меняется только при монтировании панели (`panel.tsx:86-103`; зависимости effect — `tabKey, initialUrl`, они не меняются). Ядро при клике по чипу вкладки лишь снимает `hidden` с ячейки, тело остаётся смонтированным (`dockkit: hidden:!y`, тело рендерится, как только показано, при `keepMounted`); перемонтирования/повторного `activateSession` не происходит. ResizeObserver при показе зовёт `setSessionRect`, но там `visible && activeTabId === tabId` → `false` (`engine.ts:339-343`). Сигнал, которым это чинится, ядро уже отдаёт: `useTabInfo().tab.visible` (`sr.js:4875`; `sr-README:105` — «`tab.visible` … excludes background Sessions»), но панель читает только `tab.id`/`navigation.params` (`index.tsx:188-197`).
**Что сделать:** считать активной вкладку по `tab.visible` (+`sidebar.expanded`) и вызывать `engine.activate`/`setVisible` на каждом переходе; не трогать `display` док-вкладок руками — видимостью ячейки управляет dockkit; для агента хранить отдельный `engineActiveTab` (иначе команды уходят в последнюю *смонтированную*, в т.ч. из другого чата).

**P0 | LRU-вытеснение и idle-GC уничтожают гостя живой (смонтированной) панели — восстановления нет**
`createSession` вытесняет LRU при `sessions.size >= 6` (`engine.ts:197-200`), `collectIdleSessions` закрывает 15-минутные (`engine.ts:390-397`, таймер `875`). Панель вытесняемой вкладки остаётся смонтированной, но `Session` удалена и контейнер вынут из DOM → пустая панель: effect не перезапускается, `activateSession` повторно не зовётся. `lastActiveAt` обновляется только в `activateSession` (`engine.ts:329`), а не по факту просмотра/ввода, поэтому выгрузить можно страницу, с которой человек работает. При 6 вкладках живёт 6 гостей, каждый — отдельный renderer-процесс (реально 0.5–1 ГБ суммарно; *не измерено*), а 7-я вкладка молча гасит чужую страницу.
**Что сделать:** refcount смонтированных панелей (не вытеснять их), пересоздание гостя по visible-переходу (закрывается той же правкой, что P0 выше), обновление `lastActiveAt` на visible/ввод, лимит — в конфиг + сообщение пользователю. Побочно: host не чистит `tabState`/`evidenceByTab`/`pendingVerifications` при закрытии вкладки (`index.ts:184,245,281`; console ≤200, pageScan ≤200) — медленный рост состояния процесса.

**P0 | Контейнер гостя живёт в DOM панели → любой unmount не по «крестику» убивает гостя, а движок об этом не знает**
`createSession` вешает контейнер на `host` (div панели), а не на `document.body` (`engine.ts:213-216`) — это расходится с планом `docs/architecture-v2.md:69-70, 86-89` (инвариант I1 «гость живёт вне React», контейнер в body + `position:fixed`). `detachSession` только ставит `display:none` (`engine.ts:346-352`), контейнер остаётся в поддереве, которое React удаляет → `<webview>` отвязывается, гость уничтожается, lease в main удаляется по `destroyed`, но `Session` остаётся с мёртвым `guest`. Повторное монтирование той же вкладки получит существующую сессию (`ensureSession`, `engine.ts:183-191`) и мёртвый guest: пустая панель, `hasGuest:true`, все команды падают. Триггеры: выгрузка/перезагрузка плагина (ядро: «Collapse, presentation changes and plugin disposal do not invoke close handlers» — `sr-README:109`), замена вкладки, ретиринг background-view. Сворачивание панели и смена чата, наоборот, тела НЕ размонтируют (`keepMounted`; `sr-README:107`) — это по коду ядра, живьём не проверено.
**Что сделать:** на `destroyed` обнулять `guest`+`lease`; при активации, если guest мёртв или контейнер не в документе — пересоздавать, а не переиспользовать; либо вернуть body-слой из плана, но тогда нужны z-index/обрезка по rect панели.

**P1 | Нет обработки смерти гостя и нет повторной резервации (FR-1); lease утекает в main**
Слушаются только `dom-ready`/`did-navigate(-in-page)`/`page-title-updated`/`console-message`/`did-fail-load` (`engine.ts:249-279`); нет `destroyed`/`render-process-gone` — в эталоне они есть и дают `dropGuest()`+release (`ref-browser.js:1208-1211`). Крах процесса гостя = зомби навсегда. Сторож 4 с только пишет статус и `attachFailures` (`engine.ts:285-289`): lease не освобождается и повторной резервации нет, хотя FR-1 её требует (матрица ссылается на `panel.tsx`, которого в этой роли больше нет). В main lease лежит в `leases` без TTL (`main.js:10484-10514`), одноразовость держится на `lease.attached = true`, которое не сбрасывается (`main.js:10544-10551`) → повторный attach возможен только с НОВЫМ lease.
**Что сделать:** на `destroyed`/`render-process-gone` — закрыть/пересоздать сессию; в сторож добавить `release` + одну новую резервацию; вынести в `/health` число живых гостей и lease (сейчас снаружи не видно).

**P1 | «Long-poll» не long-poll: опрос 2.5 с без защиты от наложения и без инвалидации base**
Host отвечает немедленно `204` (`index.ts:913-918`), клиент зовёт `poll` каждые 2500 мс плюс сразу при старте (`engine.ts:868-869, 501-512`) → ~2 HTTP-запроса за 2.5 с на окно (poll+report), задержка команд до 2.5 с. Флага «тик уже идёт» нет: `act_batch` (до 10×5 с + 150 мс, `engine.ts:543-564`) и `verify` (reload + 1.5 с + 5 с, `engine.ts:810-849`) держат `tickOnce` десятки секунд, а `setInterval` запускает новые тики → параллельные `poll` и конкурентные `executeJavaScript` в одном госте. `base` ставится один раз (`engine.ts:502-511`) и никогда не сбрасывается; `poll`/`report` глотают все ошибки (`transport.ts:62-75, 78-88`) → после смены маршрута движок «подключён, но глух», статус не меняется (`misses` растёт только в фазе probe). В фоновом окне Electron приглушает таймеры (backgroundThrottling по умолчанию) — команда может ждать десятки секунд, а движок знает об этом только как `hidden`.
**Что сделать:** мьютекс на `tick` (или настоящий long-poll с серверным hold+timeout); после N подряд неудач сбрасывать `base` и писать это в статус/`/health`; после команды опрашивать немедленно, не полагаясь только на `setInterval`.

**P1 | Гейт «скрытая панель» смотрит на видимость окна, а не вкладки; на скрытой панели verify/capture дают мусор**
Движок отправляет `hidden: document.visibilityState === 'hidden'` (`engine.ts:861`), host по нему кидает `E_TAB_HIDDEN` (`index.ts:1484`). Это видимость всего окна: при свёрнутом правом сайдбаре или неактивном чипе (`tab.visible=false`) `hidden=false` → verify идёт по скрытой странице (ложный fail по box) и `capturePage` может вернуть пусто (у движка это уже видно как «снимок: изображение пустое (панель скрыта?)», `engine.ts:667`). Корректный сигнал есть: `tab.visible` (`sr.js:4875`) + `sidebar.expanded`.
**Что сделать:** отдавать в host `visible`/`expanded`/`paneActive`, заменить `hidden` на «не видно ни окно, ни вкладку», по нему же гейтить `ui_verify`/`ui_screenshot` с понятной ошибкой без ретраев.

**P1 | Partition не переживает рестарт DSH и не разделён по workspace**
`main.js:10500`: `partition = dsh-sidebar-browser-${randomUUID()}`, без `persist:` → in-memory сессия (сравни: аккаунт-вью использует `persist:dsh-platform-…`, `main.js:6807`) → после рестарта DSH теряются все логины/куки/локальное хранилище гостя, хотя комментарий ядра обещает «workspace storage survives» (`main.js:10496, 10516-10519`). Плагин передаёт константу `'startapus-browser'` (`engine.ts:68, 236`), а не реальный workspace/cwd; эталон резолвит `cwd:<path>`/`session:<id>` (`ref-browser.js:1426`) → все DSH-workspace делят один профиль гостя.
**Что сделать:** на клиенте инжектить `workspaces` и передавать cwd/workspace-key как эталон; персистентность — требование к main (пункт ядру/в ТЗ), а в UI/доках не обещать «вход сохранится».

**P1 | Владение teardown по-прежнему неявное: релиз держится на побочном эффекте удаления DOM**
`closeSession` удаляет контейнер и зовёт `release` (`engine.ts:355-372`), `disposeSession` по контракту ядра не релизит (`engine.ts:375-387`). Но если контейнер уже не в DOM (см. P0 выше) или гость уничтожился сам, релиза не будет вовсе: lease останется в main до перезагрузки окна/краха (`releaseAll` — `main.js:10604-10610`). Неопределённость маскирует мёртвый код: `registerLeaseReleaser`/`releaseLeaseFor` не вызываются никем (`tabs.ts:69-113`), `closeRequested` и `crop` в движке не используются (`engine.ts:81, 89, 151-154, 809, 859`), а `props.actions.closeTab` не существует — ядро даёт `tab.actions.close()/openTab` (`sr.js:2001-2030`; матрица это уже признаёт).
**Что сделать:** один владелец — `engine.closeSession` (идемпотентный, ловит «lease уже нет»; `main.release` идемпотентен, `main.js:10520-10525`), вызывать его и из `disposeSession`; удалить мёртвые хуки; `ui_close_tab` либо закрывать настоящую вкладку через `tab.actions.close()`, либо переименовать в `ui_unload_page` (сейчас вкладка остаётся в полосе, а панель пустеет).

**P1 | Мультиклиент: очередь и цель агента глобальны, «авторизация» — один заголовок**
Host держит одну очередь `commands` на процесс (`index.ts:225`), один `clientKey` (`index.ts:248`), а все команды ставит с `tab:'*'` (`index.ts:418`) → любой поллящий клиент забирает любую команду; `clientKey` = последний опросивший, поэтому `ui_*` уходят в последний поллящий рендерер. Десктоп-шелл создаёт одно primary-окно (`main.js:12890`), но тот же host открывается в браузере (наш Web GUI `127.0.0.1:62395`): там `dshDesktop` без `browser` (`preload-app.cjs:877`) → гость не создаётся, но poll-цикл всё равно конкурирует за команды. `/client/*` проверяет только заголовок `x-startapus-client: 1` (`index.ts:890-896`) — любая локальная страница может забирать команды и подсовывать evidence. Отдельно: в `/client/event` `state` берётся ДО обновления `clientKey` из body (`index.ts:925-928`), а часть полей пишется в `state`, часть — через прокси `client` → при смене tabKey `lastCommand`/`closeTabResult`/`guestState`/`pageScan` могут попасть в чужую вкладку.
**Что сделать:** id клиента (lease/таб) в каждом запросе + очередь на клиента; явный `tabKey` в агентских инструментах (в аудите это H5); токен панели (`window.dsh.getAuthToken()` уже есть) вместо маркера; `state` брать после разрешения ключа.

**P2 | Риски обновления ядра: контракт не проверяется, часть API используется впустую**
Приватное, на чём стоит плагин (проверено по коду ядра):
1. `window.dshDesktop.browser.acquire/release` (`preload-app.cjs:771-772`) + `DesktopBrowserGuests` (`main.js:10482+`), обязательный протокол `src="about:blank#<lease>"` и точный `partition` в `will-attach-webview` (`main.js:10544-10551`).
2. `<webview>` доступен только в primary-окне: `webviewTag: primary` (`main.js:11967`) — переход ядра на WebContentsView (как у Claude) убивает весь гостевой путь.
3. `ctx.get('sidebarRight')`/`ctx.inject(['sidebarRight','sidebarRightTabs'])` + `openTab` (`tabs.ts:27-61`).
4. `registerCloseHandler` бросает при повторной регистрации (`sr.js:2195-2200`), а плагин регистрирует его вне `ctx.effect` (`index.tsx:119-123`) → после перезагрузки клиентского плагина новый модуль молча не получает close-события (старый handler смотрит в мёртвый `closingTabs`) и F3/P0-сценарий срабатывает чаще.
5. `keepMounted`, `multiple`, `priority`, слоты `sidebar.right.pane.tab(.title)` и форма `useTabInfo` ({sidebar,panel,tab.visible,navigation,signal,actions}) — `sr.js:4875`, `sr-README:85`.
6. host: `ctx.inject(['webServer'])` + `server.register({kind:'prefix'})` (`index.ts:2389-2404`).
7. `browser.onOpenRequested` не используется, хотя `allowpopups` выставлен (`engine.ts:245`): `target=_blank` ядро отклоняет и шлёт событие, которое никто не слушает (`main.js:10588-10602`; эталон слушает — `ref-browser.js:1172-1176`) → ссылки «в новую вкладку» молча не работают.
Рукопожатия версий нет: `probe` проверяет только `response.ok` (`transport.ts:49-59`), а `/health` уже отдаёт `buildRev` и `capabilities` (`index.ts:867-887`) — их никто не сверяет, клиент и host могут разъехаться по набору команд без единого сигнала. `keepMounted: true` ставится безусловно (`index.tsx:162`), тогда как эталон гейтит его наличием моста (`ref-browser.js:1606`).
**Что сделать:** сверять `buildRev`/`capabilities` при probe и отдавать `capability` в инструменты; close-handler в `ctx.effect` с unregister; подписка на `onOpenRequested` → `openStartapusTab`; iframe-фолбэк (как у эталона при `desktop === undefined`) либо честное «вне desktop панель не работает».

## 2. Три главных риска

1. **Пустая панель при обычном переключении вкладок/чатов** — прямое нарушение AC-2 и главного сценария (человек выделяет элемент). Живая приёмка это не ловит, потому что проверяет `/health.sessions` (реестр), а не пиксели панели.
2. **Необратимая деградация гостя** (unmount-убийство, LRU/GC, смерть процесса гостя) при `hasGuest:true` в отчётах: агент «делает вид», что работает, а панель пуста — и длинная сессия/6 вкладок делают это штатным путём.
3. **Канал**: 2.5-секундный опрос без мьютекса и без инвалидации base + глобальная очередь без id клиента — при фоне окна, втором клиенте и перезагрузке host команды теряются или уходят не туда, и это не видно ни в статусе, ни в `/health`.

## 3. Что проверить экспериментом (приложение я не запускал)

1. **Возврат на вкладку (главный P0).** Два `ui_new_tab` в одном чате → дождаться загрузки → клик по чипу первой вкладки. Ожидаемо пусто, при этом `ui_guest_state` вернёт живую страницу, а `ui_screenshot` — пустоту. Лог: `tail -f ~/.dsh/startapus-host.log`.
2. **Шесть вкладок/вытеснение.** Открыть 7 вкладок → `curl -s http://127.0.0.1:62395/startapus-browser/health | jq '{tabs,counters,queued}'` до/после → клик по первой вкладке. Параллельно `ps -Ao rss,command | grep -i "DeepSeek Harness Helper (Renderer)" | head` — прирост RSS на гостя (оценка «0.5–1 ГБ» в отчёте не измерена).
3. **Рестарт DSH и потеря логинов.** Залогиниться на сайте в панели → `Cmd+Q` → запуск → тот же сайт. Ожидаемо не залогинен (подтверждает non-persist partition). Дополнительно: `ls ~/Library/Application\ Support/DeepSeek\ Harness/Partitions` — для in-memory partition каталога не будет.
4. **Перезагрузка клиентского плагина.** Выключить/включить плагин в менеджере плагинов → закрыть вкладку крестиком → `curl -s …/health | jq '{tabs,sessions}'` (зомби в реестре?), затем открыть вкладку заново. В логе смотреть парность `apply:start`: сейчас там 49 записей без `pid`/bootId, поэтому reload от рестарта не отличить — `probe('apply:start')` стоит дополнить pid.
5. **Смерть гостя.** Найти pid renderer'а гостя (`ps -Ao pid,command | grep "guest-instance-id"`) и убить его → `ui_guest_state`/`ui_open`. Ожидаемо: ошибки без восстановления, панель мёртвая до закрытия вкладки.
6. **Приглушение таймеров.** Скрыть окно (`Cmd+H`) на 2 минуты → `ui_open` → замерить по логу `at` в `cmd:delivered` и `cmd:processed`.
7. **Наложение тиков.** Одновременно `ui_act` с 10 действиями и `ui_open`. В логе — два `cmd:delivered` без `cmd:processed` между ними и/или действия не по порядку.
8. **Фальшивый клиент.** Сначала поставить `ui_open`, затем сразу:
   `curl -s -H 'x-startapus-client: 1' -X POST http://127.0.0.1:62395/startapus-browser/client/poll -d '{"tabKey":"evil"}'`
   Ожидаемо команда уйдёт «evil» — доказывает отсутствие адресации/авторизации. Осторожно: съедает команду.
9. **Скрытая панель.** Свернуть правый сайдбар → `ui_verify` на готовой задаче. Ожидаемо не `E_TAB_HIDDEN`, а pass/fail по нулевому box или пустой снимок (подтверждает F6).

Не проверено (нужен живой прогон): реальное число и RSS гостей; поведение при выгрузке клиентского плагина без перезагрузки страницы; живёт ли гость при сворачивании сайдбара; задержка команд в фоне.
