## 1. Сценарий по шагам: где рвётся и где теряется контекст

| Участник | Шаги | Что он получает |
|---|---|---|
| Человек | открыть вкладку → ввести адрес → `⌖` → клик → проза → отправить = **6** | чип `ЭлементN` и `setStatus('выбран: …')` внизу панели |
| Агент | `ui_evidence` → `task_create` → `task_update{triaged}` → (правка кода) → `ui_verify` → `task_get` = **5 вызовов**, из них 1 слепой (`ui_verify`); а каждый `ui_read_page`/`ui_select`/`ui_screenshot` — это +2 вызова (второй, чтобы увидеть результат первого) | `verified` в `state` — **и всё** |
| Человек после отправки | 0 действий | ничего: ни задачи, ни критерия, ни вердикта, ни замера |

Три обрыва контекста:
1. **После пика.** Человек отдал «вот тут плохо», а машиночитаемый критерий (`expected`, `method`, `tolerance`) придумывает модель, и человек его больше не видит. «Ожидаемо 16px» из головы человека не попадает никуда.
2. **Между задачей и проверкой.** Агент сам переводит задачу в `triaged` (`src/index.ts:1822-1824`) — шага «человек утвердил» в продукте нет, хотя ТЗ §2 шаг 4 и §5 (`approvedBy`) его требуют.
3. **После `ui_verify`.** `task_get` возвращает `state`, но не возвращает измеренное значение (`src/index.ts:449-461`). Агент физически не может процитировать «16px», а человек не видит вердикта. «Доказал» — это слово модели, а не артефакт.

## 2. Находки

### P0-1 | Человек выпадает из цикла ревью: нет UI задачи, критерия и вердикта
**Проблема.** Продукт обещает «аннотация = воспроизводимый тест-кейс» и «ручное подтверждение постановки» (ТЗ §1–2), но у человека в панели есть только тулбар, адрес и одна строка статуса. Задачу, критерий и вердикт видит только модель; `triage` делает агент сам.
**Доказательство.** `grep -rn "task_|triaged|verified" src/client/` → **0 совпадений**; вся панель — `src/client/panel.tsx:198-238` (6 кнопок + поле адреса + `snapshot.status`); `task_update` разрешает `triaged` любому без следа человека (`src/index.ts:1822-1824`); `ReviewTask` (`src/index.ts:93-109`) не имеет `approvedBy`/`provenance` (есть в ТЗ §5); `get task_get` отдаёт `taskView` без вердикта (`src/index.ts:449-461`, `:1797-1806`).
**Что сделать.** Рейка «Задачи» в панели: список с `state`, критерием, кнопкой «Утвердить» (только человек → `approvedBy: human`), результатом замера и вердиктом. `task_update{triaged}` без `approvedBy` → `E_APPROVAL_REQUIRED` (по образцу `ui_open`).

### P0-2 | Доказательство может быть тавтологией: критерий задаёт тот, кто его же и «доказывает»
**Проблема.** `task_create` принимает `expected` от агента, а `ui_evidence` тем же вызовом отдаёт `computed`. Ничто не мешает агенту поставить `expected = observed` — тогда `ui_verify` пройдёт по построению, и это будет `verified`. Человек, не видя критерия, отличить проверку от её имитации не может.
**Доказательство.** `createTask` берёт `acceptance` прямо из аргументов модели (`src/index.ts:1248-1255`); `evaluateAcceptance` сравнивает только `observed` vs `expected` (`src/index.ts:1161-1190`); `computed` в evidence — `src/client/verify-scripts.ts:109-115`; `Acceptance` не имеет `baseline`/`source` (`src/index.ts:113-118`), хотя `baseline` объявлен в ТЗ §5.
**Что сделать.** В `Acceptance` добавить `baseline` (снимок текущего значения в момент постановки) и `source: 'human'|'token'|'agent'`; отказ, если `expected` совпадает с `baseline` и `source: 'agent'` (`E_TAUTOLOGY`); человек утверждает `expected` в панели (см. P0-1).

### P0-3 | `ui_read_page` не отдаёт страницу, а `ref_N` не принимает ни один инструмент
**Проблема.** «Обзор страницы» — слепой инструмент: он только ставит команду, а забрать дерево нечем. Единственный доступ к узлам — `ui_find`, но он требует непустой запрос, т.е. до него надо **угадать** строку. При этом описание `ui_find` обещает, что `ref_N` можно «сразу передавать в `ui_act`», а `ui_act` принимает только CSS-селектор. Это ровно тот контракт, который в Claude работает: `read_page` отдаёт дерево сразу, `ref_N` идут в `computer`/`form_input`.
**Доказательство.** `ui_read_page` всегда `enqueue` и никогда не возвращает `client.pageScan` (`src/index.ts:1602-1613`, `:1623-1635`); `ui_status` показывает только `pageScan.total/at/error` (`src/index.ts:1418`); `ui_find` без скана → `E_NO_COVERAGE` (`src/index.ts:1626`); описание «можно сразу передавать в `ui_act`» (`src/index.ts:1617`) против `ui_act{op,selector,value}` (`src/index.ts:1656-1664`, `:1692-1694`); `ref` генерится заново каждым сканом (`src/client/verify-scripts.ts:242-243`), а скан обрывается на `limit` без пагинации (`:233`). Цитата Claude: `read_page` → «Each interactive element is tagged `[ref_N]` for use with `computer`/`form_input`/`find`… limited to 50000 characters».
**Что сделать.** Эхо-ответ с TTL: `ui_read_page` при свежем (`≤30 с`, тот же `url`) `pageScan` возвращает `{ tree: [{ref,role,name,selector,visible}], total, truncated, next }`, иначе `queued` + `E_PENDING` (не новая постановка команды). Принимать `ref` (`ref_12`) в `ui_select/ui_act/ui_verify/task_create`, резолвя его на клиенте по последнему скану; `ref` сохранять в локаторе задачи. `ui_find` не требует скана — сам сканирует, если данных нет.

### P1-4 | Флаг `reload` не доезжает до замера: проверка после правки кода видит старый CSS
**Проблема.** Ветку замера уже перевели на «settle без reload» (`verifyNeedsReload/verifySettleMs`), но флаг `reload` до неё не доходит: `task_create.reload` принимается и молча выбрасывается, в команду `verify` он не кладётся. Значит перезагрузку нельзя включить вообще, а для сценария «агент починил CSS/HTML в коде» замер по умолчанию читает **старый** CSS из уже загруженной страницы → `reopened`; после трёх таких попыток breaker (`E_LIMIT`) требует пере-пик. Это ломает «починил → доказал» для правок, которые не подхватываются HMR. Описание `ui_verify` при этом по-прежнему говорит «панель перезагружает страницу».
**Доказательство.** `src/client/engine.ts:859-861` — `const reload = verifyNeedsReload(command.args); if (reload) view.reload?.()`: решение зависит от `command.args.reload`, а `ui_verify` кладёт только `taskId/selector/tag/method/property` (`src/index.ts:1516-1522`); `task_create.reload` объявлен (`src/index.ts:1725`), но в `Acceptance` не сохраняется (`:1248-1255`); описание — `src/index.ts:1484`; breaker — `src/index.ts:1509-1510`. QA независимо нашёл тот же разрыв «правила есть, движок их не звал» ([`qa-expert.md`](qa-expert.md)); на 08:17 area- и element-ветки уже зовут правила (`src/client/engine.ts:742-744`, `:859-861`).
**Что сделать.** Хранить `reload` в задаче и класть в команду (`src/index.ts:1516`); добавить `ui_verify{reload}` для разового переопределения; по умолчанию `false` (не сбрасывать страницу ревьюера), но с честным `hint`, что для правок без HMR нужен `reload: true`; описание привести к факту; `reload` возвращать в ответе, чтобы агент знал, что именно измерялось.

### P1-5 | Вердикт и замер не сохраняются и не возвращаются — «доказательство» существует только в логе
**Проблема.** После `ui_verify` на руках у агента остаётся `state: verified` и `attempts`. Измеренное значение, причина pass/fail, URL/вьюпорт момента проверки, `tabId` — не сохраняются в задаче и не отдаются ни одним инструментом. Человеку предъявить нечего; агент не может процитировать число, а значит не может и «доказать».
**Доказательство.** `taskView` (`src/index.ts:449-461`) отдаёт метаданные задачи и `state/attempts`, но без измеренного значения; хендлер verify пишет в задачу лишь `state`+`attempts`, а `reason` уходит в `probe('verify:done', …)` (`src/index.ts:1097-1120`), т.е. в `~/.dsh/startapus-host.log`, недоступный инструментам (единственный приёмник — `appendFileSync`, `src/index.ts:24-32`); `ui_verify` возвращает только `{queued,commandId}` (`src/index.ts:1523`).
**Что сделать.** `task.lastVerify = { pass, observed, expected, method, property, reason, at, url, viewport, dpr, reload }`; отдавать в `task_get` и в ответе `ui_verify`; добавить `ui_report{id}` → markdown-доказательство для человека: критерий, замер, «до/после», путь к снимку, вкладка.

### P1-6 | Два разных генератора evidence: если элемент выбрал агент, он видит заметно меньше
**Проблема.** Evidence человека и evidence агента — разные скрипты. У человеческого пика есть `pseudo ::before/::after`, `ancestors`, `fragment ≤50`, `outerHTML`, `theme/reducedMotion/colorScheme`, 48 computed-свойств; у `ui_select` — своя копия из 24 свойств без всего перечисленного. Для дизайн-ревью это критично: нет `letter-spacing`, `z-index`, `padding-top`, `grid-template`, псевдоэлементов, цепочки фонов (а без неё контраст текста не посчитать).
**Доказательство.** `src/client/picker-source.ts:182-243` (`payloadOf`: `pseudo`, `ancestors`, `fragment`, `outerHTML`, `env.theme`, 48 свойств из `COMPUTED_PROPERTIES`, `:22-40`) vs `src/client/verify-scripts.ts:105-142` (свой список 24 свойств, без `pseudo/ancestors/fragment/outerHTML/theme`). Общий дефект обоих: из `computed` выбрасываются `0px/auto/none/normal` (`picker-source.ts:132-138`, `verify-scripts.ts:114`) — `margin: 0px` и `gap: 0` становятся неотличимы от «свойства нет», а именно отступы и есть предмет ревью. Параметра «какие свойства» нет ни там, ни там — а Claude считает `preview_inspect` лучшим инструментом для цветов/шрифтов/отступов именно точечным запросом (`docs/claude-reference-analysis.md:24`).
**Что сделать.** Один генератор (`evidenceScriptFor(target, props?)`), `picker` и `select` — только разные входы (`ref`/`selector`); добавить `props?: string[]`, вернуть цепочку фонов предков и `contrastRatio`; нули отдавать (`0px` — факт), а не фильтровать.

### P1-7 | Нет текстового чтения страницы: ревью текста и контента нечем закрыть
**Проблема.** Мандат ревью включает класс `copy` (`ui_template`), но чтобы прочитать страницу, у модели есть только `ui_find` по интерактиву и `text ≤300` одного элемента из evidence. Статью, документацию, лендинг прочитать нельзя — а именно это самое частое «нашёл косяк в тексте».
**Доказательство.** `pageScanScript` собирает только `a/button/input/textarea/select/summary/details/label` и `h1..h6` (`src/client/verify-scripts.ts:233-243`), текст узла обрезан до 120 символов (`:229`); `text` в evidence — 300 (`:128`); ТЗ FR-41 «Текст страницы article/main сначала — **не реализовано**» (`startapus-browser-tz.md:96`); в Claude `get_page_text` «сначала article/main, затем body» (`docs/claude-reference-analysis.md:23`).
**Что сделать.** `ui_page_text{scope:'main'|'body'|'selection', maxChars, offset}` — article/main-first, лимит + пагинация (как `read_page` 50k), пометка `trust.untrusted`. Дёшево и закрывает целый класс ревью.

### P1-8 | Асинхронный конверт без ожидания: 10 из 19 `ui_*` слепые, отказы — строки, а не типы
**Проблема.** Почти каждый второй вызов только ставит команду, а результат приходит следующим вызовом **этого же** инструмента, который ставит команду заново. Худший случай — `ui_screenshot`: путь к своему снимку приходит в `previous` только следующим вызовом, и он опять снимает. Плюс 25 инструментов против 14 браузерных в эталоне (`docs/claude-reference-analysis.md:20-30`) и отказы в виде `Error('E_*: текст')` без `code/retryable/hint` — модели приходится парсить прозу и догадываться, повторять или нет.
**Доказательство.** `ui_screenshot` возвращает `previous: client.crop` и тут же `enqueue('capture')` (`src/index.ts:1699-1716`); `ui_pick/ui_open/ui_pick_area/ui_viewport/ui_read_page/ui_select/ui_act/ui_screenshot/ui_new_tab/ui_close_tab` = 10 слепых; результат живёт в `ui_status` (`src/index.ts:1401-1425`); все отказы — `throw new Error('E_…: текст')` (`src/index.ts:406, 430-444, 1491-1512`), поля `retryable`/`hint` из ТЗ §4 отсутствуют (grep по `retryable` → 0); объявления инструментов: `src/index.ts:1322-1828`.
**Что сделать.** Единый конверт `{ ok, status:'done'|'pending', code?, retryable?, hint?, data }` + параметр `awaitMs` (ждать отчёт до N мс) во всех командных инструментах → один вызов вместо двух-трёх. `ui_verify` возвращает вердикт, `ui_screenshot` — путь своего снимка. Слить/переименовать: `ui_pick`+`ui_pick_area`+`ui_select` → `ui_target{mode:'human'|'area'|'selector'|'ref'}`; `ui_evidence`+`ui_area`+`ui_guest_state` → `ui_inspect{target}`; `ui_new_tab`/`ui_close_tab`/`ui_tabs` → `ui_tabs{action}`. Это сокращает поверхность с 25 до ~19 (а если слить `ui_verify`+`ui_report` и `ui_console`+`ui_page_text` — до ~17) и убирает 4 способа выбрать элемент.

### P1-9 | Мультивкладка: команда уходит первой ответившей вкладке, `tab` нет, URL не сверяется
**Проблема.** Все команды бродкастятся (`tab: '*'`), забирает их та вкладка, что первой опросила host. При двух открытых вкладках `ui_verify`/`ui_read_page`/`ui_select` могут выполниться **на другой странице**, а вердикт ляжет в задачу от первой. `task.url` сохраняется, но перед замером не сверяется, поэтому «verified» может относиться к другому URL. Параметра `tab` нет ни в одном инструменте, хотя `ui_tabs` список отдаёт.
**Доказательство.** `enqueue` ставит `tab:'*'` (`src/index.ts:418`); poll отдаёт команду первому совпавшему (`src/index.ts:911`); ни одна схема `ui_*` не содержит `tab` (`src/index.ts:1322-1717`); `ui_verify` передаёт только `taskId/selector/tag/method/property` (`src/index.ts:1516-1522`), а `task.url` пишется в `createTask` (`src/index.ts:1281`) и больше не читается; `E_ENV_MISMATCH` объявлен в ТЗ (`startapus-browser-tz.md:126`), в коде — **0** вхождений. Аудит H5 рекомендовал `tabId?` — не сделано.
**Что сделать.** `tab` во всех адресных инструментах + адресная доставка (`tab: key`); перед замером `task.url === session.url`, иначе `E_ENV_MISMATCH` (не `reopened`); `ui_tabs` помечает активную.

### P2-10 | UX панели: одна строка статуса на всё, нет индикации, область недоступна человеку, вытеснение молчаливое
**Проблема.** В ежедневной работе раздражает: (1) строка загрузки страницы, действия пикера, команды агента и ошибки пишутся в **одну** строку и затирают друг друга — пока агент работает, человек не знает, загрузилась ли страница; (2) нет индикатора загрузки/ошибки в адресной строке и нет индикатора «агент подключён» — человек не знает, увидит ли модель его пик; (3) кнопки выделения области в тулбаре нет, `ui_pick_area` доступен только агенту, т.е. «выделил область» человек начать не может; (4) при лимите 6 гостей седьмая вкладка молча теряет страницу (сообщение проскакивает в той же строке статуса), а вкладок в сайдбаре при этом может быть сколько угодно.
**Доказательство.** `src/client/panel.tsx:198-238` — 6 кнопок и поле адреса, единственный индикатор — `snapshot.status` (`:236`); `setStatus` зовут панель, пикер и все команды агента (`src/client/engine.ts:550-700`, `:636-732`); кнопки области нет в тулбаре (`src/client/panel.tsx:201-225`), `ui_pick_area` — только у агента (`src/index.ts:1527-1535`); `MAX_SESSIONS = 6` (`src/client/engine.ts:70`), вытеснение — только текст в статус (`src/client/engine.ts:197-201`); логотип/тайтл уже есть (`src/client/index.tsx:35-45`, `:241-245`).
**Что сделать.** Три независимых индикатора: загрузка страницы (полоса в тулбаре), транспорт (`● агент`), действие агента (`выбирает/снимает/проверяет`). Кнопка «область» рядом с `⌖`. На вкладке бейдж «страница выгружена» + «перезагрузить» в один клик. Адресная строка показывает состояние (`загрузка`, `ошибка`, `небезопасно`). ## 3. Минимальный набор изменений, который даёт 80% пользы

1. **L** — UI задач в панели: список, критерий, «Утвердить», вердикт с замером; `triaged` только человеком (P0-1).
2. **M** — эхо-ответ инструментов вместо слепых round-trip: `ui_read_page` отдаёт дерево, `ui_verify` — вердикт, `ui_screenshot` — путь, `awaitMs` в конверте (P0-3, P1-8, первая половина).
3. **M** — `task.lastVerify` + `ui_report` (markdown-доказательство человеку и агенту) + `baseline` в критерии с `E_TAUTOLOGY` (P0-2, P1-5).
4. **S** — один генератор evidence на человека и агента, `props?: string[]`, не выбрасывать `0px`, цепочка фонов и `contrastRatio` (P1-6).
5. **S** — `ref_N` как вход во всех адресных инструментах (P0-3).
6. **S** — verify без reload по умолчанию, `reload` доезжает из задачи в команду (P1-4).
7. **S** — `tab` в инструментах + сверка `task.url` → `E_ENV_MISMATCH` (P1-9).
8. **M** — `ui_page_text` article-first с пагинацией (P1-7).
9. **M** — типизированные отказы `{code, retryable, hint}` и слияние 25 инструментов до ~19 по смыслу (P1-8, вторая половина).
10. **S** — три индикатора в панели + кнопка «область» + бейдж вытесненной страницы (P2-10).

**80/20 одной строкой:** дать человеку экран задачи с утверждаемым критерием и отдавать вердикт с замером в ответе инструмента (L+M) — это закрывает «доказал»; затем отдавать содержимое страницы и `ref_N` в ответе (M+S) — это закрывает «починил без скриншота»; остальное (reload, tab, typed errors, индикаторы) — дешёвые S-правки, которые убирают раздражение в ежедневной работе.
